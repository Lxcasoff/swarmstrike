Running swarmstrike

A team of specialist agents works an authorized penetration test, challenges each other's findings, and produces a report. This is how it fits together, and how you drive it yourself.

Before anything else

This runs against systems you are authorized to test, and it enforces that in code rather than asking you to remember it. It will not start without a signed engagement contract, and it refuses commands outside that contract's scope at the moment they would run. If you do not hold written authorization for the targets, there is nothing here for you.

01Get it running

One command does everything a script is allowed to do.

git clone https://github.com/Lxcasoff/swarmstrike
cd swarmstrike
./run.sh

One script does the lot: checks your prerequisites, installs the package with the dashboard, builds the toolbox image the agents' commands run inside, generates a signing key into .env at mode 600, asks for your Anthropic API key if it is not set, scaffolds a contract, and opens the console. Running it again is safe — a key, a contract or an image that already exists is left alone — so it is also the command to run after a git pull. --tui runs a campaign in the terminal instead, --setup-only stops after setup, and --rebuild forces a fresh toolbox image.

You need Docker and Python 3.11+. Node 20+ as well, because the agent harness drives the Claude Code CLI, which is a Node program — or skip Node and use the server container, which carries its own. Where the full toolbox cannot build for lack of a package mirror, the script falls back to a minimal image with curl, nuclei, httpx and ffuf, and tells you it did.

The three steps the script will not take

It stops before signing the contract. That is deliberate: the contract is the written authorization the whole tool answers to, and a script that signed one anyway would be forging exactly the thing the rest of the design exists to enforce.

# 1. Say who authorized this test, against what, and until when.
$EDITOR engagement.yaml

# 2. Sign it. Any edit after this point is detected and refuses the campaign.
source .env
swarmstrike engagement sign engagement.yaml

# 3. Confirm it says what you think it says. Do this every engagement.
swarmstrike engagement check engagement.yaml app.client.example 8.8.8.8

Then run it

./run.sh                                # console on http://127.0.0.1:8787
./run.sh --tui                          # live view in the terminal

To see the interface before you have a contract at all, start the server and open http://127.0.0.1:8787/?demo. That replays a scripted campaign through the same renderers the live view uses, with no backend and no target contacted.

02The contract is the authority

Everything the swarm may do is declared in one signed file. Nothing else grants permission.

engagement.yaml is not documentation that happens to sit beside the code. It is parsed, and the scope guard refuses commands against it at execution time. A target you forget to name is a target the swarm will refuse to touch; a rule you leave at its default is a rule that holds.

BlockWhat it decides
engagementClient, mission, and the written authorization: who signed it, their role, the reference. Reproduced on the report cover and in the audit header.
windowStart, end, timezone, and optional daily hours. A command outside the window is refused, not queued.
scopeDomains, addresses, ranges and URLs. Private ranges count only when named here. Loopback and link-local never count, whatever you write.
exclusionsCarve-outs that beat scope. An excluded address inside an in-scope range stays excluded.
rules_of_engagementIntensity, request rate, and the forbidden list: destruction, denial of service, data modification, persistence, social engineering, pivoting out of scope.
credential_testingOff unless you authorize it, and then only against the test accounts you name.
exploitationWhether proof-of-concept exploitation is allowed, and whether it stops at proof.
red_teamThe post-exploitation phases, each behind its own flag. All off by default.
arbitrary_executionWhich of the three execution tiers the agents get. Shell and scripts are off by default.
budgetCost, token and wall-clock ceilings. The campaign stops at the first one reached, and still reviews and reports what it has.
contactsEmergency stop contact, and the conditions that must halt the campaign.

The file is HMAC-signed with a key kept outside the repository. Verification is a fingerprint over the contract's canonical form, so reformatting it does not matter and changing a value does:

$ swarmstrike engagement verify engagement.yaml
✗ contract content does not match its fingerprint — it was edited after signing

03What stops it going wrong

The agents run unattended, so none of this is advice in a prompt. It is all in code.

Scope is checked, not trusted

Every command is parsed and placed against the contract before it runs. The guard fails closed: a command whose targets it cannot positively locate inside the contract is refused rather than let through. You can interrogate it directly, which is the right way to satisfy yourself before an engagement:

$ swarmstrike engagement check engagement.yaml www.example.org 8.8.8.8 169.254.169.254
www.example.org   allow    scope.domain   matches in-scope domain example.org
8.8.8.8           refuse   scope.miss     not in any in-scope range
169.254.169.254   refuse   hard_deny      loopback/link-local, never in scope

Loopback and link-local are refused regardless of the contract, which keeps the swarm off its own toolbox and off the cloud metadata endpoint. Forbidden categories are matched before scope is consulted, because an in-scope target does not license destroying it.

Three execution tiers, and no shell by default

TierWhat it isWhat checks it
RecipeOne of 73 declarative tool definitions, each with typed parameters.Fully checked. The argument vector is built from validated parameters, so there is no string for an agent to inject into.
PipelineOutput of one allowlisted binary piped into another, across containers.Scope-checked, and the filter stages are restricted to a short allowlist that excludes every interpreter.
ShellAn arbitrary command or script. Off unless the contract turns it on.Contained and logged, and it requires approval. It is not scope-enforced, and the tool says so rather than implying a guarantee it cannot keep.

Agents never execute on the host

Every command runs in a throwaway container with a read-only root filesystem, all capabilities dropped, and bind mounts limited to the campaign workspace. Preflight proves the workspace mount actually landed by writing a token and having a container read it back — because the alternative is tools that run, write into nothing, and report success.

Everything is recorded, and the record can be checked

Commands are logged before they run, each entry hash-chained to the one before it and flushed to disk before the command starts. Afterwards the chain verifies, which is what lets a client audit what was actually done:

$ swarmstrike audit verify campaigns/ENG-2026-014-20261023-1412-a7f3c1
✓ chain intact across 1,284 entries (head 5e8671140d671e67…)

One honest caveat: the agent name on each entry is a string the model fills in, because subagent identity does not reach the tool server. Every entry that carries a name also records whether it is one the campaign actually dispatched, so the field cannot quietly pass for identity.

Approval is deny-by-default

Anything that cannot be statically checked goes to an approval gate. Unattended, it denies: a campaign does not approve its own shell. In the console and the terminal view, requests appear for you to allow or refuse, with a timeout.

Credential material the target hands back

A read-only request against a broken authorization check can answer with a user table, and that lands in the evidence directory because it is the proof. Those files are not altered — an assessment that shreds its own evidence has nothing to show — but they are inventoried beside the output, recorded in the audit chain, and named in the report with instructions to treat the credentials as compromised.

Two things with no technical guard

The dashboard has no authentication and binds to localhost for that reason. A campaign record describes unremediated vulnerabilities in a client's systems, so moving it anywhere else needs a deliberate decision and something in front of it.

The server container mounts the Docker socket, because it starts a toolbox container per command. Socket access is equivalent to root on the host, so run it on a machine you treat as dedicated to the engagement.

04The console

swarmstrike serve, then http://127.0.0.1:8787. Eight views over one running campaign.

You launch from the browser: pick the specialists, point at the contract, and start. Each agent appears as an avatar whose state comes from real events — working while a tool runs, thinking while it reasons over a finding, a burst when it proposes one, a shake when the contract refuses a command. The kill switch is in the header.

ViewWhat it shows
War roomThe agents, live, with the running log of what each is doing and the campaign's spend against its ceilings.
FindingsEach finding as it is proposed, and its status as it moves through review, challenge and arbitration. Click one to read the debate behind it.
Attack pathsChains assembled from evidenced steps, not asserted in prose: a path exists here only because each step was recorded and linked.
FactsThe shared board every agent reads and writes, dead ends included. Negative results are first-class, so nobody re-runs what was already disproved.
AgentsThe roster for this campaign, which model each runs on, and what it has spent.
ToolsWhich recipes this contract authorizes, and which of those the toolbox image can actually run.
AuditThe hash-chained record, with its verification status, filterable by event.
ContractThe authority in force, with its fingerprint, so you can see what the campaign is running under.

Approval requests appear outside the tabs, so one cannot sit unnoticed behind a view you are not looking at.

05What a campaign actually does

Not a fixed sequence of phases. A search, with the loop in code.

A playbook of phases spends budget on steps that stopped making sense three findings ago. Instead a lead reads the board each round and decides what is worth doing next; the round structure, the duplicate-work check, the no-progress guard and the budget check are in code, so they hold whether or not a model remembers them.

1

Read the board

The lead gets a digest: the attack surface so far, established facts, dead ends not to reassign, evidenced paths, findings proposed, work already claimed, and the tools each specialist can actually run on this image.

2

Assign

It returns a reading and a set of tasks, each to a named specialist with a task key. A key already claimed is refused, so two rounds cannot duplicate work.

3

Work

Specialists run in parallel up to a limit, each with only the tools its domain and the contract allow. They record assets, facts and proposed findings as they go, and evidence every claim.

4

Stop or go again

The loop ends on a round ceiling, a budget ceiling, the kill switch, the lead declaring the surface exhausted, or two consecutive rounds that produced nothing new.

5

Challenge

Every finding is reviewed by a second specialist from a different discipline, then attacked by a reviewer whose only job is to show it is a false positive, a duplicate or mis-scored. An arbiter rules.

6

Report

Assembled deterministically from the record, so it cannot claim a finding the database does not hold or a severity the arbiter did not set.

Useful flags: --domain to narrow the roster, --search-rounds to cap the loop, --review-rounds for the challenge depth, --network to reach targets on a Docker network, --resume to continue a campaign, and --tui for the terminal live view.

06Who is on the team

Eight specialists, three reviewers, and six post-exploitation roles your contract has to switch on.

Specialists

  • recon
  • network
  • web
  • api
  • cloud
  • ad
  • code
  • crypto

Challenge roles

  • skeptic
  • arbiter
  • reporter

The skeptic argues against each finding, the arbiter rules on the disagreement, the reporter writes the narrative from the confirmed record.

Red team — each behind its own contract flag

  • foothold
  • privesc
  • lateral
  • persistence
  • exfil
  • detection

Off by default, and off individually: authorizing lateral movement does not authorize persistence. With a phase switched off, its tools are not merely refused — they are not offered, because an agent told a capability exists will keep spending budget reaching for it.

Work is routed by role rather than run on one model: the lead and the arbiter get the strongest model because their judgment compounds, specialists get a mid-tier model, and mechanical summarisation gets the cheap one. The contract's budget caps the total either way.

07What comes out

A client deliverable in Markdown, HTML and PDF — not a scanner dump.

Testing follows PTES, web work follows the OWASP Testing Guide, and severities are CVSS v3.1. Nothing reaches the report that has not been reviewed, challenged and adjudicated.

§SectionContents
1Executive summaryOverall risk in a sentence a non-technical reader can act on, the severity counts, and the ordered list of what to fix first.
2Scope and authorizationWhat was in scope, what was excluded, and the rules of engagement — marked where they were enforced technically rather than by convention.
3MethodologyThe phases, the coverage figures, and how each finding was validated.
4Confirmed findingsPer finding: description, impact, reproduction a client can run, remediation, CVSS vector with its sub-scores, MITRE ATT&CK mapping, and the assessor note recording the challenge it survived.
5Attack pathsMulti-step chains, each step evidenced. Where none was demonstrated it says so, and says that is a statement about what was shown rather than an assurance.
6Unproven weaknessesWhat was suspected but could not be confirmed inside the rules, handed to the client's team to verify.
7CoverageThe attack surface identified, by asset type.
8Remediation roadmapEvery confirmed finding in priority order with the concrete action.
9Engagement recordChain verification, contract fingerprint, commands issued and refused, any halt that was overruled and by whom, an inventory of evidence files holding credential material, and the limits of the assessment.
 
swarmstrike report campaigns/<campaign-id> -f all   # md, html, pdf
swarmstrike report campaigns/<campaign-id> --narrate # prose summary

08When it stops itself

The agents have the stop button, and they are told to use it.

An agent that sees a service degrading, an asset that may belong to a third party, or exposed personal data halts the whole campaign rather than continuing. You can trip the same switch from the console header, or from any shell with touch <campaign-dir>/HALT. Findings gathered before the halt stay valid and are still reported.

A halt is a judgment about something the agent just found, and that something does not go away. Clear the file, resume, and the next agent reaches the same endpoint and halts again — so resuming needs a record of your answer:

swarmstrike acknowledge <campaign-id> \
    --pattern "/rest/memories" \
    --ruling "Stock seed data on a lab host the operator owns. Record it and continue." \
    --operator "Your Name"

A halt raised for a condition you have ruled on is declined, and the agent is told what you decided so it records a finding and carries on. This deliberately weakens the strongest guardrail in the tool, so it leaves marks:

  • The ruling exists only because a person ran that command.
  • The pattern must name the condition. Matching is by substring, so a two-word pattern would overrule halts you have never seen — short ones are refused.
  • A ruling with no decision text, or no operator name, is refused.
  • Creating one and relying on one both go into the audit chain.
  • The report discloses every overruled halt, in your words, with your name against it.
  • An unreadable rulings file overrules nothing.
  • A ruling answers one condition. The campaign still halts for anything else.

Practise on something you own first

The repository ships a lab: two deliberately vulnerable applications on an isolated Docker network, and a contract that authorizes testing them. lab/README.md has the commands. Nothing leaves the host, no third party is involved, and it is the right place to learn what the console shows you before an engagement depends on it.

10Where the line is

Version 1.0 has been exercised end to end. It has not been exercised everywhere.

Proven

276 tests cover the contract and its signing, scope enforcement, the audit chain, the approval gate, the three execution tiers, the fact graph, the search loop, CVSS scoring, and the report's escaping of target-controlled evidence. Every command shape that must never reach a target has a test proving it does not.

Two full campaigns ran against the lab: 155 commands, nine confirmed findings including an unauthenticated SQL injection and a user-record disclosure, a chain verified across 186 entries, inside a $4 budget. Eight defects came out of those runs that no unit test would have found — a digest offering the lead tools the image did not carry, agent claims that never closed and stalled the search two rounds early, a comma-separated target list that read as no target at all, credential material written to evidence unflagged, a halt that made resuming impossible, and a fact link to a non-existent key that silently dropped the only attack-path step. Each is fixed, each has a test.

Not proven

AreaStatus
A real client engagementThe lab is a lab. The prompts in particular will want iteration against findings a client actually cares about.
Attack pathsHas never produced a chain from real data. On the lab engagement that is arguably correct — exploitation stopped at proof and authentication testing was unauthorized, so the findings are independent pre-auth disclosures with nothing to chain — but the section stays unproven.
Red team phasesImplemented, gated behind contract flags the lab contract left off.
Active Directory and cloudSpecialists and recipes exist. No target has been available to run them against.
Start narrow

Before running this against anything real: read swarmstrike/scope.py, run swarmstrike engagement check against your contract until you are satisfied it refuses what it should, and start with a small roster on a small scope.
